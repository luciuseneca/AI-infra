# Векторные базы данных и Qdrant

## Кратко

- **Векторная БД** хранит числовые представления объектов и находит ближайшие к запросу по заданной метрике. Модель преобразует текст, изображение или другой объект в вектор. База отвечает за хранение, отбор и ранжирование.
- **Точный поиск** сравнивает запрос со всеми подходящими векторами. **Приближённый поиск** (ANN) обходит часть индекса и может пропустить настоящего соседа. Qdrant использует HNSW для индексирования плотных векторов.
- **Qdrant** хранит точки с ID, векторами и метаданными. В одном запросе можно искать по смыслу, ограничивать выборку по метаданным, искать по словам и объединять результаты.
- Для RAG полезно измерять три разных результата. Насколько ANN совпадает с точным поиском, находит ли поиск релевантные фрагменты и подтверждает ли найденный контекст итоговый ответ.
- Ниже есть два примера. Первый показывает точный поиск и изоляцию по метаданным на трёхмерных векторах. Второй использует мультиязычную модель и гибридный поиск по русскоязычной базе знаний.

## 1. Что хранит векторная база

Запрос «Не могу войти, забыл пароль» и инструкция «Восстановление доступа к учётной записи» могут иметь мало общих слов. Модель эмбеддингов может поставить их рядом в векторном пространстве, если в ходе обучения научилась улавливать такую связь. Поисковый сервис сравнит эмбеддинг запроса с эмбеддингами инструкций и вернёт ближайшие. Для точного кода ошибки `AUTH-401` лучше предусмотреть лексический поиск либо точное совпадение по отдельному полю.

**Эмбеддинг** — вектор признаков, вычисленный моделью. Координаты плотного эмбеддинга обычно интерпретируют совместно. **Размерность** — число координат. **Индекс** — структура, которая помогает быстро находить кандидатов. **Top-k** — до `k` лучших результатов после применения ограничений. **Payload** в Qdrant — JSON-метаданные точки, например `tenant_id`, `doc_id`, `status`, URL и текст фрагмента.

| Задача | Что представляют векторы | Что ещё нужно |
|---|---|---|
| Семантический поиск | Запрос и фрагменты текста | Метаданные, релевантность по размеченным запросам |
| RAG | Вопрос и фрагменты базы знаний | Права доступа, ссылки на источники, генерация ответа |
| Рекомендации | Пользователей и товары в совместимом пространстве | Наличие, ограничения каталога, бизнес-ранжирование |
| Похожие изображения | Признаки изображений | Фильтры каталога и метрики на визуально похожих объектах |
| Поиск дубликатов | Документы, изображения или описания | Калиброванный порог и проверка кандидатов |

~~~mermaid
flowchart LR
    A["Документы"] --> B["Извлечение текста и разбиение"]
    B --> C["Эмбеддинги фрагментов"]
    C --> D["Qdrant: точки и индексы"]
    E["Вопрос пользователя"] --> F["Эмбеддинг вопроса"]
    F --> G["Поиск с фильтрами доступа"]
    D --> G
    G --> H["Переранжирование кандидатов"]
    H --> I["Контекст для LLM со ссылками"]
~~~

Модель для поиска часто используют как **биэнкодер**. Документы кодируются заранее, запрос — в момент поиска. Иногда для обеих сторон используют одну модель с разными инструкциями, например `query:` и `passage:` у E5. Два вектора одинаковой длины могут принадлежать несовместимым пространствам. Поэтому вместе с версией модели фиксируют предобработку, размерность и метрику. [Карточка multilingual E5](https://huggingface.co/intfloat/multilingual-e5-small)

## 2. Как измеряется близость

| Метрика | Формула для векторов x и y | Как ранжируется | Что учитывает |
|---|---|---|---|
| `Cosine` | `dot(x, y) / (norm(x) × norm(y))` | Больше — ближе | Угол, при ненулевых нормах |
| `Dot` | `sum(x[i] × y[i])` | Больше — ближе | Угол и длины векторов |
| `Euclid` | `sqrt(sum((x[i] − y[i])²))` | Меньше — ближе | Расстояние L2 |
| `Manhattan` | `sum(abs(x[i] − y[i]))` | Меньше — ближе | Расстояние L1 |

Возьмём запрос `q = [1, 0]` и два объекта `a = [1, 0]`, `b = [3, 4]`. Косинус равен `1` для `a` и `0,6` для `b`. Скалярное произведение даёт `1` и `3`, поэтому `Dot` меняет порядок. Для единичных векторов `dot = cosine`, а квадрат расстояния L2 равен `2 − 2 × cosine`. Все три метрики тогда задают один порядок при одинаковом наборе кандидатов. Qdrant при использовании `Cosine` нормализует векторы при загрузке и вычисляет сходство скалярным произведением. Метрику выбирают по контракту модели и проверяют на собственных запросах. [Коллекции и метрики Qdrant](https://qdrant.tech/documentation/manage-data/collections/)

Значение `score` зависит от метрики и способа ранжирования. Косинус `0,82` сам по себе не сообщает вероятность релевантности. При переходе на другую модель, метрику или RRF прежний порог потребуется калибровать заново. Для расстояний направление порога отличается от метрик сходства. [Query API Qdrant](https://api.qdrant.tech/api-reference/search/query-points/)

### Плотные, разреженные и мультивекторы

| Представление | Как устроено | Для чего подходит |
|---|---|---|
| Плотный вектор (*dense*) | Массив фиксированной длины, обычно с большим числом ненулевых координат | Семантика, похожие изображения, рекомендации |
| Разреженный вектор (*sparse*) | Пары `индекс → вес` для ненулевых координат | Совпадения терминов и поиск с обучаемыми разреженными моделями |
| Мультивектор (*multivector*) | Матрица из нескольких плотных векторов одного поля | Позднее взаимодействие, например сопоставление токенов в ColBERT |

**Именованные векторы** — способ хранить несколько полей у одной точки. Например, `title_dense` представляет заголовок, `image` — картинку, `body_sparse` — разреженное представление текста. Поисковый запрос выбирает поле через `using`. **Мультивектор** может быть значением одного такого поля. При `MaxSim` каждый вектор запроса находит самое похожее представление в документе, затем эти максимумы складываются. Если в запросе 16 векторов и в документе 120, прямой расчёт делает до `16 × 120 = 1 920` сравнений пар на документ. Поэтому такой этап часто запускают по ограниченному набору кандидатов. [Типы векторов](https://qdrant.tech/documentation/manage-data/vectors/), [позднее взаимодействие](https://qdrant.tech/documentation/tutorials-search-engineering/using-multivector-representations/)

## 3. Точный поиск и ANN

При точном поиске алгоритм вычисляет близость запроса к каждому подходящему вектору и сохраняет лучшие `k`. Для `N` векторов размерности `d` вычисление метрик из таблицы требует порядка `N × d` операций. Для миллиона векторов по 768 координат один полный проход затрагивает 768 млн координат. При хранении `float32` это примерно 2,86 ГиБ исходных данных в одном проходе. SIMD и пакетная обработка ускоряют вычисления. При достаточно большом объёме ограничителем может стать пропускная способность памяти. Если фильтр оставил 200 точек, точный расчёт по ним может оказаться дешевле обхода графа.

| Подход | Как сокращает работу | Цена |
|---|---|---|
| Flat | Перебор всех подходящих векторов | Точные соседи, объём работы растёт линейно по числу кандидатов |
| HNSW | Переходит по рёбрам графа между близкими точками | Память под граф, время построения, возможные пропуски |
| IVF | Делит векторы на группы вокруг центроидов и проверяет выбранные группы | Обучение центроидов, компромисс между числом просматриваемых групп и полнотой |
| IVF + PQ | Внутри выбранных групп считает приближённые расстояния по компактным кодам | Дополнительная погрешность квантования, возможный пересчёт по оригиналам |

IVF и IVF + PQ здесь приведены для сравнения подходов. Для плотного ANN Qdrant использует HNSW. Выбор индекса зависит от данных, фильтров, размера top-k, интенсивности записей и бюджета на хранение. [Индексы Faiss](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes), [индексы Qdrant](https://qdrant.tech/documentation/manage-data/indexing/)

### HNSW под капотом

HNSW (*Hierarchical Navigable Small World*) строит многослойный граф. Каждый объект есть на нижнем слое. Лишь случайная доля объектов попадает выше, причём верхние слои становятся разреженными. Рёбра соединяют подходящих соседей. При построении используется эвристика, которая помогает сохранить разнообразные направления обхода.

1. **Вставка в граф.** Алгоритм выбирает максимальный уровень новой вершины, спускается от входной точки и ищет кандидатов на соседство. На нужных уровнях выбирает связи и при необходимости сокращает списки соседей.
2. **Запрос.** На верхних уровнях жадный обход приближается к области запроса. На нижнем уровне поиск держит набор ближайших кандидатов и расширяет его через соседей. Несколько путей позволяют обойти локальный тупик, в котором застрял бы простой жадный поиск.
3. **Результат.** Поиск останавливается по критерию алгоритма и возвращает лучшие найденные точки. Пропущенная область графа может содержать более близкую точку.

| Параметр Qdrant | На что влияет | Что обычно меняется при росте |
|---|---|---|
| `m` | Бюджет связей графа | Память и время построения растут, качество может вырасти |
| `ef_construct` | Ширина поиска соседей при построении | Индексация дороже, структура графа может стать лучше |
| `hnsw_ef` | Ширина обхода на запросе | Задержка и полнота обычно растут |
| `exact: true` | Выбор точного векторного поиска | Можно построить эталон для сравнения ANN |

`m` и `ef_construct` относятся к построению. `hnsw_ef` можно менять на запросе. У HNSW нет универсальной гарантии логарифмической задержки для любого распределения данных и фильтров. При настройке полезно сначала измерить кривую «полнота — p95» для разных `hnsw_ef`, затем сравнить конфигурации графа, если нужная точка на кривой недостижима. [Статья о HNSW](https://arxiv.org/abs/1603.09320), [параметры индекса Qdrant](https://qdrant.tech/documentation/manage-data/indexing/)

## 4. Как устроен Qdrant

Qdrant — сервер векторного поиска с открытым исходным кодом на Rust. Его можно развернуть самостоятельно или использовать как управляемый сервис. Для интеграции доступны HTTP API и gRPC. [Репозиторий Qdrant](https://github.com/qdrant/qdrant), [локальный запуск и порты](https://qdrant.tech/documentation/quickstart/)

| Уровень | Что содержит | Зачем нужен |
|---|---|---|
| Коллекция | Точки и конфигурацию векторных полей, индексов и хранения | Определяет область поиска и правила сравнения |
| Точка | ID типа `uint64` или UUID, векторы, опциональный payload | Представляет фрагмент, объект каталога или другой индексируемый элемент |
| Шард | Часть данных коллекции | Делит данные и нагрузку между узлами |
| Реплика шарда | Копию одного шарда | Поддерживает доступность и распределение чтений |
| Сегмент | Локальную порцию точек, хранилища векторов и payload, индексы | Позволяет читать, записывать и оптимизировать части шарда |
| WAL | Журнал изменений перед их применением | Позволяет восстановить незавершённое применение записей |

**Запись.** Запрос маршрутизируется к нужному шарду. Операция регистрируется в WAL и получает номер. Затем изменения применяются к сегментам, допускающим запись. Версии помогают избежать применения устаревших операций при восстановлении. Повторный `upsert` с тем же ID перезаписывает точку. Для частичного обновления предусмотрены операции над payload и отдельными векторами. [Хранение](https://qdrant.tech/documentation/manage-data/storage/), [операции над точками](https://qdrant.tech/documentation/manage-data/points/)

**Оптимизация.** Фоновый процесс строит индексы, объединяет мелкие сегменты и освобождает место, занятое удалёнными точками. Пока сегмент перестраивается, запросы продолжают работать. Рост объёма данных без индекса может увеличить задержку из-за точного перебора. При обычных настройках `wait=true` ждёт применения операции к сегменту. `indexed_only` может исключать часть свежих данных из поиска. `prevent_unoptimized` откладывает видимость некоторых записей до индексации и в сочетании с `wait=true` может задержать обработку очереди обновлений. Эти режимы меняют контракт свежести выдачи. [Оптимизатор](https://qdrant.tech/documentation/ops-optimization/optimizer/), [видимость при индексации](https://qdrant.tech/documentation/search/low-latency-search/)

**Чтение.** Qdrant направляет запрос на нужные шарды. Внутри них ищет по сегментам, подбирая способ поиска с учётом размера и фильтров. При простом векторном запросе локальные кандидаты объединяются в общий top-k по оценке. Прибавка шардов даёт больше ёмкости, но запрос по всей коллекции затрагивает больше частей. На p99 может влиять самая медленная из них. [Распределённое развёртывание](https://qdrant.tech/documentation/scaling/distributed_deployment/), [индексация](https://qdrant.tech/documentation/manage-data/indexing/)

### Почему фильтр меняет поиск

Пусть среди миллиона точек 0,5% видны конкретному клиенту. Глобальный top-10 с последующим отбором по `tenant_id` легко окажется пустым, хотя разрешённых точек 5 000. Корректная цель — найти top-10 **внутри разрешённого множества**.

- **Мало подходящих точек.** Индекс payload помогает найти их по метаданным. По небольшому набору удобно точно посчитать сходство.
- **Подходит большая доля точек.** Обход HNSW часто позволяет избежать полного перебора.
- **Промежуточный случай и сложные фильтры.** После исключения части вершин граф хуже связывает разрешённые области. Qdrant добавляет рёбра, опираясь на индексированные поля payload. Для комбинаций условий этих связей иногда мало. ACORN может проверить соседей второго порядка, когда прямые соседи отфильтрованы. Это добавляет работу на запросе и может повысить полноту.

Создавай payload-индексы для регулярно используемых фильтров до массовой загрузки, чтобы соответствующие связи учитывались при построении HNSW. Для точного совпадения строки подходит `keyword`, для чисел и диапазонов — соответствующий числовой тип, для поиска по словам — текстовый индекс. В логике фильтра `must` требует выполнения всех условий, `should` — хотя бы одного из перечисленных, `must_not` исключает совпадения. У массива объектов используй `nested`, если несколько условий должны совпасть в **одном** элементе. Иначе запись с продавцом A в одном предложении и ценой до 1000 в другом может пройти оба независимых условия. [Индексация и ACORN](https://qdrant.tech/documentation/manage-data/indexing/), [фильтрация](https://qdrant.tech/documentation/search/filtering/), [статья об ACORN](https://arxiv.org/abs/2403.04871)

## 5. Практика. Точный поиск через REST

Примеры рассчитаны на Qdrant **1.20.0**. Первый использует стандартную библиотеку Python 3.12, для второго понадобятся `sentence-transformers` и доступ к весам модели. Команды запуска подходят для PowerShell при работающем Docker в режиме Linux-контейнеров. Порт опубликован только на loopback, а именованный том сохраняет данные при удалении контейнера. [Локальный старт](https://qdrant.tech/documentation/quickstart/), [релиз Qdrant 1.20.0](https://github.com/qdrant/qdrant/releases/tag/v1.20.0)

```powershell
docker run --detach --name qdrant-demo --publish 127.0.0.1:6333:6333 --volume qdrant_demo_data:/qdrant/storage qdrant/qdrant:v1.20.0
Invoke-RestMethod http://127.0.0.1:6333/readyz
```

Когда сервер готов, сохрани код как `qdrant_demo.py` в UTF-8 и запусти `python qdrant_demo.py`. Код использует отдельную коллекцию `demo_vectors_v1`. При повторном запуске те же ID будут записаны заново.

```python
import json
from urllib.error import HTTPError
from urllib.request import Request, urlopen

BASE_URL = "http://127.0.0.1:6333"


def api(method, path, body=None):
    data = None if body is None else json.dumps(body).encode("utf-8")
    request = Request(
        BASE_URL + path,
        data=data,
        headers={"Content-Type": "application/json"},
        method=method,
    )
    try:
        with urlopen(request, timeout=30) as response:
            return json.load(response)["result"]
    except HTTPError as error:
        details = error.read().decode("utf-8", errors="replace")
        raise RuntimeError(f"{method} {path}: HTTP {error.code}: {details}") from error


def tenant_filter(tenant_id):
    return {"must": [{"key": "tenant_id", "match": {"value": tenant_id}}]}


def ensure_payload_indexes(collection, schemas):
    existing = api("GET", collection)["payload_schema"]
    for field, schema in schemas.items():
        if field not in existing:
            api("PUT", f"{collection}/index?wait=true", {
                "field_name": field,
                "field_schema": schema,
            })


def main():
    collection = "/collections/demo_vectors_v1"
    if not api("GET", f"{collection}/exists")["exists"]:
        api("PUT", collection, {"vectors": {"size": 3, "distance": "Cosine"}})
    ensure_payload_indexes(collection, {"tenant_id": "keyword"})

    rows = [
        (1, "team-a", "Восстановить пароль", [0.8, 0.6, 0.0]),
        (2, "team-a", "Настроить профиль", [0.0, 1.0, 0.0]),
        (3, "team-b", "Сбросить пароль администратора", [1.0, 0.0, 0.0]),
    ]
    api("PUT", f"{collection}/points?wait=true", {
        "points": [
            {
                "id": point_id,
                "vector": vector,
                "payload": {"tenant_id": tenant_id, "title": title},
            }
            for point_id, tenant_id, title, vector in rows
        ],
    })

    query = {
        "query": [1.0, 0.0, 0.0],
        "params": {"exact": True},
        "limit": 2,
        "with_payload": ["tenant_id", "title"],
    }
    unfiltered = api("POST", f"{collection}/points/query", query)["points"]
    assert [point["id"] for point in unfiltered] == [3, 1]

    hits = api("POST", f"{collection}/points/query", {
        **query,
        "filter": tenant_filter("team-a"),
    })["points"]
    assert [point["id"] for point in hits] == [1, 2]
    for point in hits:
        print(f"{point['id']}  {point['score']:.3f}  {point['payload']['title']}")


if __name__ == "__main__":
    main()
```

## 6. Практика. Гибридный поиск по базе знаний

Плотный поиск полезен для перефразированных вопросов. BM25 оценивает совпадения токенов. Он повышает вклад редких терминов, ограничивает эффект повторений и учитывает длину текста. Например, запрос «Что делать при AUTH-401, если я не помню пароль?» можно отправить в обе ветки. Эмбеддинг помогает найти инструкцию о восстановлении доступа, а лексическая ветка добавляет кандидатов, где встречается код ошибки.

У BM25 в Qdrant есть два пути. Можно индексировать **разреженные векторы** с весами терминов, используя инвертированный индекс для доступа к спискам точек по ненулевым координатам. В Qdrant 1.20 можно также включить BM25 непосредственно на **текстовом индексе payload** и передать текст в Query API. В примере выбран второй путь. Для идентификаторов, которые должны совпасть целиком, заведи отдельное поле `keyword`. Текстовый анализатор может разделить `AUTH-401` на токены. [BM25 через разреженные векторы](https://qdrant.tech/documentation/inference/inference-bm25/), [BM25 на текстовом индексе](https://qdrant.tech/documentation/search/text-search/full-text-search/), [индексы Qdrant](https://qdrant.tech/documentation/manage-data/indexing/)

Например, у разреженного запроса ненулевые координаты `7 → 0,7` и `90 → 0,2`. У документа — `7 → 0,4` и `15 → 0,9`. Их скалярное произведение равно `0,7 × 0,4 = 0,28`, поскольку совпала только координата 7. Поиск по разреженному индексу обрабатывает списки точек по координатам 7 и 90. В JSON координаты и веса передаются как два параллельных массива `indices` и `values`. Обе стороны должны использовать одинаковое соответствие между терминами или признаками и координатами. [Разреженные векторы Qdrant](https://qdrant.tech/documentation/manage-data/vectors/#sparse-vectors)

### Как объединяются списки

У косинуса и BM25 разные шкалы. **RRF** (*Reciprocal Rank Fusion*) опирается на место в каждом списке. Упрощённая запись для равных весов — `sum(1 / (c + rank))`, где позиции считаются с единицы и складываются только вклады списков, в которых точка присутствует. Константа сглаживает разницу между позициями. В API Qdrant своя конвенция нумерации позиций и поддерживается настройка весов. **DBSF** (*Distribution-Based Score Fusion*) использует нормализованные оценки каждой ветки. Выбирай способ объединения по разметке и проверяй чувствительность к глубине кандидатов. [Гибридные запросы и формулы Qdrant](https://qdrant.tech/documentation/search/hybrid-queries/)

### Запуск с multilingual E5

Создай окружение рядом с `qdrant_demo.py` и установи зависимость. Первый запуск загрузит веса `intfloat/multilingual-e5-small`. Модель выдаёт 384 координаты, для поиска по фрагментам ей передают префиксы `query:` и `passage:`, в том числе для русского текста. Модель имеет лимит в 512 токенов, поэтому длинные документы разбивают до кодирования. [Карточка модели E5](https://huggingface.co/intfloat/multilingual-e5-small)

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install sentence-transformers
```

Сохрани следующий код как `qdrant_hybrid.py` рядом с первым файлом. Он переиспользует HTTP-запросы, проверку индексов и фильтр доступа из первого примера.

```python
from sentence_transformers import SentenceTransformer

from qdrant_demo import api, ensure_payload_indexes, tenant_filter

COLLECTION = "/collections/demo_kb_e5_v1"
MODEL = "intfloat/multilingual-e5-small"


def main():
    encoder = SentenceTransformer(MODEL)
    if not api("GET", f"{COLLECTION}/exists")["exists"]:
        api("PUT", COLLECTION, {
            "vectors": {"dense": {"size": 384, "distance": "Cosine"}},
        })
    ensure_payload_indexes(COLLECTION, {
        "tenant_id": "keyword",
        "text": {"type": "text", "tokenizer": "word", "scoring": True},
    })

    chunks = [
        (101, "team-a", "account/reset",
         "Чтобы восстановить доступ, запросите письмо для смены пароля."),
        (102, "team-a", "account/session",
         "Ошибка AUTH-401 означает, что сессия истекла. Войдите снова."),
        (103, "team-a", "profile/avatar",
         "Чтобы изменить аватар, откройте настройки профиля."),
        (201, "team-b", "admin/auth",
         "AUTH-401 в панели администратора требует проверить служебную учётную запись."),
    ]
    embeddings = encoder.encode(
        [f"passage: {text}" for _, _, _, text in chunks],
        normalize_embeddings=True,
    )
    api("PUT", f"{COLLECTION}/points?wait=true", {
        "points": [
            {
                "id": point_id,
                "vector": {"dense": vector.tolist()},
                "payload": {"tenant_id": tenant, "source": source, "text": text},
            }
            for (point_id, tenant, source, text), vector in zip(
                chunks, embeddings, strict=True
            )
        ],
    })

    question = "Что делать при AUTH-401, если я не помню пароль?"
    query_vector = encoder.encode(
        f"query: {question}", normalize_embeddings=True
    ).tolist()
    scope = tenant_filter("team-a")
    response = api("POST", f"{COLLECTION}/points/query", {
        "prefetch": [
            {"query": query_vector, "using": "dense", "filter": scope, "limit": 20},
            {
                "query": {"text": question},
                "using": "text",
                "filter": scope,
                "limit": 20,
            },
        ],
        "query": {"rrf": {}},
        "limit": 2,
        "with_payload": ["tenant_id", "source", "text"],
    })
    hits = response["points"]
    assert hits and all(hit["payload"]["tenant_id"] == "team-a" for hit in hits)
    for hit in hits:
        payload = hit["payload"]
        print(f"{hit['score']:.3f}  {payload['source']}  {payload['text']}")


if __name__ == "__main__":
    main()
```


Запрос возвращает до двух фрагментов с идентификаторами источников. Оба предварительных поиска получают один и тот же фильтр доступа. Это позволяет им тратить лимит кандидатов только на доступные точки. Для прикладного сравнения отдельно выполни плотный и BM25-запросы с тем же фильтром и сопоставь их с гибридной выдачей. Числа из RRF нельзя читать как косинус. Маленький корпус показывает устройство запроса. Для оценки качества нужны размеченные вопросы и более представительный набор документов. [Примеры BM25 и RRF](https://qdrant.tech/documentation/search/hybrid-queries/)

### От поиска к RAG

1. **Индексируй фрагменты.** Сохраняй заголовок раздела, идентификатор документа, версию и положение фрагмента. Разбивай по структуре текста и проверяй размер токенизатором модели. Перекрытие фрагментов помогает сохранять контекст на границах, но увеличивает объём индекса и число повторов.
2. **Собери кандидатов с ограничениями.** Сначала учитывай доступ, статус и нужную версию. Подбери глубину `prefetch` на валидации. Всё, что отсутствует в наборе кандидатов, недоступно следующей стадии.
3. **Переранжируй при необходимости.** Кросс-энкодер получает пару «вопрос и фрагмент» и оценивает её совместно. Он дороже биэнкодера, поэтому его обычно применяют к небольшому списку. Для позднего взаимодействия можно использовать мультивекторы и `MaxSim`.
4. **Собери контекст.** Объедини соседние куски, убери повторы и ограничь количество фрагментов из одного документа. Если нужен один результат на документ, Qdrant поддерживает группировку по полю payload.
5. **Сформируй ответ с источниками.** Передай LLM текст и идентификаторы источников. Если доступные документы не дают ответа, приложение может вернуть сообщение о недостатке данных. Проверяй ссылки и подтверждённость утверждений отдельно от качества retrieval. [Многостадийные запросы и группировка](https://qdrant.tech/documentation/search/hybrid-queries/), [мультивекторное переранжирование](https://qdrant.tech/documentation/tutorials-search-engineering/using-multivector-representations/)

## 7. Как измерять качество и скорость

| Уровень | С чем сравнивать | Метрики |
|---|---|---|
| ANN-индекс | Точный top-k при той же модели, метрике и фильтре | Доля совпадений, p50/p95/p99, QPS |
| Поиск для пользователя | Релевантные документы или фрагменты по разметке | Recall@k, MRR, nDCG@k |
| RAG целиком | Ожидаемые ответы и поддерживающие источники | Корректность, доля подтверждённых утверждений, задержка ответа |

**Полнота ANN.** Пусть точный поиск вернул `[4, 9, 2, 8, 6]`, а ANN — `[4, 9, 8, 5, 6]`. Пересечение содержит 4 точки из 5, полнота ANN равна 0,8. Если фильтр оставил меньше `k` точек, дели на фактический размер точного результата. Случаи с пустым эталоном учитывай отдельно. На границе top-k точки с одинаковой оценкой могут меняться местами, поэтому оговори обработку ничьих.

**Релевантность поиска.** Если по разметке у вопроса четыре подходящих документа и в top-5 есть три из них, Recall@5 равен 0,75. Если первый релевантный документ стоит третьим, его вклад в MRR равен `1/3`. nDCG учитывает позиции и степень релевантности. Для RAG заранее выбери единицу оценки — документ или фрагмент. Десять почти одинаковых фрагментов из одного документа могут занимать весь top-10 и давать слабый охват базы знаний.

Практический порядок проверки:

1. Подготовь запросы из реальных сценариев. Выдели короткие запросы, коды ошибок, перефразирования, разные языки, запросы с узкими фильтрами и случаи без ответа.
2. Зафиксируй набор данных. Для плотной ветки получи эталон с `exact: true`. При дополнительном квантовании отключи его в эталонном запросе через `quantization.ignore: true`, чтобы сравнивать с полноточным набором, если он доступен.
3. Сравни ANN на нескольких `hnsw_ef`. Проверяй, что коллекция успела построить нужные индексы. На маленькой коллекции или узком фильтре Qdrant может выбрать точный перебор, и тогда изменение `hnsw_ef` ничего не покажет.
4. На разметке сравни плотный, лексический, гибридный поиск и вариант с переранжированием. Отдельно оцени запросы с обязательными ограничениями и долю запросов, для которых поиск дал пустой результат.
5. Прогони нагрузку при разных уровнях параллелизма. Измерь p95 и p99 с прогретым и холодным кэшем, при одновременных записях и перестроении сегментов. Отделяй время эмбеддинга запроса, сети, Qdrant и переранжирования.

Улучшение полноты ANN при плохой разметочной релевантности означает, что индекс точнее воспроизводит соседей текущей модели. Дальше нужно проверять сами эмбеддинги, разбиение документов и схему ранжирования. [Настройка точности Qdrant](https://qdrant.tech/documentation/manage-data/quantization/), [оценка моделей при миграции](https://qdrant.tech/documentation/tutorials-operations/embedding-model-migration/)

## 8. Память, диск и квантование

Для плотных `float32` исходный объём равен `число точек × размерность × 4 байта`. Миллион векторов размерности 768 занимает около **2,86 ГиБ**. Две реплики требуют около **5,72 ГиБ** исходных векторов по кластеру. В расчёт отдельно входят HNSW, payload, payload-индексы, служебные структуры, WAL и запас под перестроение сегментов и снимки. Размерность и число именованных векторов влияют на этот расчёт напрямую.

| Настройка или метод | Механизм | Компромисс |
|---|---|---|
| Векторы на диске | Чтение через отображение файлов в память (mmap) и кэш ОС | При холодном кэше и случайных обращениях растут задержки |
| HNSW на диске | Граф тоже можно хранить на диске отдельно от векторов | Случайные переходы графа могут увеличить I/O |
| Скалярное квантование | Представляет компоненты меньшим числом бит, например 8 вместо 32 | Сырые коды в примере примерно вчетверо меньше, погрешность может изменить порядок |
| Product Quantization | Делит вектор на части и кодирует каждую индексом центра из кодовой книги | Сильное сжатие, обучение кодовых книг и приближённые оценки |
| Бинарное квантование | Кодирует компоненты малым числом бит | Экономит память, качество сильно зависит от распределения эмбеддингов |

Распространённая схема Qdrant держит компактное представление в памяти и использует его для поиска кандидатов. **Oversampling** расширяет список кандидатов, **rescoring** пересчитывает их оценки по исходным векторам. Если оригиналы на диске, пересчёт требует чтения и может поднять p99. Пересчёт может исправить порядок только среди найденных кандидатов. Коэффициенты сжатия относятся к представлению векторов, а итоговый объём сервиса зависит от хранения оригиналов и индексов. [Хранилище Qdrant](https://qdrant.tech/documentation/manage-data/storage/), [квантование и пересчёт](https://qdrant.tech/documentation/manage-data/quantization/)

## 9. Эксплуатация

### Шарды, реплики и согласованность

В кластере шарды делят данные, реплики копируют шарды. Например, у коллекции с тремя шардами и фактором репликации два шесть копий шардов в сумме. При автоматическом шардировании ID определяет маршрут записи. При пользовательском шардировании ключ помогает направить запросы к заданному подмножеству шардов. Размещай реплики одного шарда на разных узлах. Консенсус Raft координирует изменения состояния кластера и конфигураций коллекций. Операции над точками идут через путь репликации шардов со своими настройками согласованности. [Распределённое развёртывание](https://qdrant.tech/documentation/scaling/distributed_deployment/), [горизонтальное масштабирование](https://qdrant.tech/documentation/scaling/horizontal-scaling/)

| Настройка | Что контролирует | Компромисс |
|---|---|---|
| `replication_factor` | Число копий каждого шарда | Больше ресурсов, выше доступность при подходящем размещении |
| `write_consistency_factor` | Сколько реплик должно подтвердить запись для успешного ответа | При потере нужного числа реплик успешная запись становится недоступной |
| `ordering` | Порядок конкурентных записей | `weak` допускает переупорядочивание, `medium` использует динамического лидера, `strong` закрепляет лидера и зависит от его доступности |
| `consistency` | Скольким репликам отправить чтение и по какому правилу согласовать ответ | Дополнительные запросы и влияние медленных либо недоступных реплик |
| `wait` | Ждать ли применения операции перед ответом | Больше задержка записи, более понятный момент видимости при обычных настройках |

Если у шарда две реплики и требуются два подтверждения, отказ одной реплики мешает получить успешный ответ записи. При ошибке или тайм-ауте часть реплик уже могла принять обновление. Для безопасного повтора нужны стабильный ID, контроль версии и порядок событий в приложении. Даже `ordering=strong` не даёт транзакции для нескольких точек и внешней БД. [Гарантии согласованности](https://qdrant.tech/documentation/scaling/consistency-guarantees/)

### Синхронизация с источником данных

Типовая схема хранит документы и права в основной БД, а точки поиска строит как производный индекс. Транзакция основной БД сохраняет изменение и событие в outbox. Фоновый обработчик читает событие, готовит фрагменты, вычисляет векторы, записывает новые точки и убирает устаревшие. Задержку между коммитом и видимостью результата полезно измерять как отдельный показатель.

- **Повторы и порядок.** Стабильный UUID из идентификаторов клиента, документа и фрагмента позволяет безопасно повторять ту же запись. Обработка событий по ключу документа и проверка версии источника защищают от запоздалого события, которое иначе перезапишет новую версию старой.
- **Изменение разбиения.** Если раньше было пять фрагментов, а после редактирования осталось три, нужно явно удалить два старых. Для поиска с атомарной видимостью версий проектируй публикацию и фильтрацию с учётом того, что несколько upsert и delete применяются раздельно.
- **Миграция модели.** Заполняй новую коллекцию, поддерживай её актуальной, проверяй качество и переключай алиас согласованно с переключением модели запроса. Обработай удаление и изменение документов во время backfill, чтобы старые данные не появились повторно. В коллекциях с именованными векторами начиная с Qdrant 1.18 можно добавить отдельное векторное поле и позже переключить `using`. [Миграция модели в Qdrant](https://qdrant.tech/documentation/tutorials-operations/embedding-model-migration/)

### Изоляция и восстановление

- **Мультитенантность.** Для многих небольших клиентов можно использовать общую коллекцию с индексированным `tenant_id`. `is_tenant` помогает размещать данные клиента вместе. При заметном перекосе нагрузки крупного клиента можно маршрутизировать в отдельный шард. Для более строгой изоляции выбирают границы доступа и размещения исходя из требований системы. Поле `tenant_id` само по себе прав не проверяет. [Мультитенантность Qdrant](https://qdrant.tech/documentation/manage-data/multitenancy/)
- **Доступ.** Для сервиса с внешними клиентами включи TLS и аутентификацию, раздели полномочия чтения и записи, ограничь сетевой доступ к REST, gRPC и межузловому порту. Проверяй фильтр из доверенного контекста при каждом чтении и ограничивай объём возвращаемого payload. [Безопасность Qdrant](https://qdrant.tech/documentation/security/)
- **Снимки.** Храни резервные копии отдельно и проверяй восстановление на отдельном окружении. Выбирай процедуру для топологии. В распределённом режиме учитывай снимки нужных шардов и восстановление конфигурации кластера. Репликация поддерживает доступность, а резервная копия позволяет вернуться к более раннему состоянию после ошибочного удаления. [Снимки Qdrant](https://qdrant.tech/documentation/operations/snapshots/)
- **Наблюдаемость.** Собирай задержки и ошибки запросов, скорость загрузки, отставание обработки обновлений, состояние оптимизатора, объём диска и активность реплик. Проверяй `/readyz` для готовности обслуживать запросы и собирай `/metrics` по узлам. Рост p99 одновременно с дисковыми чтениями или индексацией даёт повод проверить ресурсы и план поиска. [Метрики и телеметрия](https://qdrant.tech/documentation/ops-monitoring/monitoring/)

## 10. Когда выбирать Qdrant

Qdrant подходит, когда поиск по сходству — заметная часть продукта. Например, в базе знаний нужны частые поиски с фильтрами доступа, а команда хочет отдельно масштабировать индекс, сочетать текст и векторы и настраивать соотношение полноты и задержки.

### Преимущества

- Поиск по нескольким представлениям объекта, включая плотные и разреженные векторы, через один API.
- Отбор по структурированным метаданным встроен в поиск, а индексы payload помогают планировать его выполнение.
- Многостадийный поиск позволяет формировать кандидатов и комбинировать результаты на сервере.
- Хранение в памяти и на диске, репликация, шардирование и фоновые оптимизации дают рычаги для работы с разными объёмами и нагрузками.

### Ограничения и альтернативы

Отдельный сервис добавляет сетевой вызов, синхронизацию и операционную нагрузку. HNSW и оптимизация требуют ресурсов, качество ANN зависит от данных и фильтров. Если задача в основном состоит из SQL-запросов, связей и транзакционных обновлений, проще начать с расширения существующей БД. Для точной идентификации по ID, артикулу или коду ошибки достаточно соответствующего поля и обычного индекса. Для маленькой локальной выборки полный перебор может укладываться в нужную задержку.

| Решение | Когда рассматривать | Что проверить |
|---|---|---|
| Qdrant | Самостоятельный сервис для поиска по векторам и метаданным, гибридные запросы | Нагрузку на синхронизацию, полноту с фильтрами, эксплуатацию отдельного сервиса |
| PostgreSQL + pgvector | Данные уже в PostgreSQL, полезны SQL, JOIN и транзакции с остальными таблицами | План запроса при сочетании фильтров с HNSW или IVFFlat, влияние поиска на основную БД |
| Elasticsearch | Сложившийся текстовый поиск, важны анализаторы и гибридное ранжирование | Качество векторной и лексической веток, хранение индексов, управление существующим кластером |
| Faiss | Встраиваемый офлайн-поиск, эксперименты с индексами или свой специализированный сервис | Где будут метаданные, права доступа, сетевой API и восстановление |

Для выбора сравни задержку и стоимость на одинаковом корпусе, фильтрах и целевой полноте. Бенчмарк без фильтров мало говорит о сценарии, где каждый запрос ограничен конкретным клиентом и статусом документа. [pgvector](https://github.com/pgvector/pgvector), [гибридный поиск Elasticsearch](https://www.elastic.co/docs/solutions/search/hybrid-search), [индексы Faiss](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes), [фильтрация в Qdrant](https://qdrant.tech/documentation/search-patterns/vector-search-filtering/)

## 11. Типичные ошибки и диагностика

| Симптом | Что проверить первым |
|---|---|
| Размерности совпадают, но выдача выглядит случайной | Версию модели, `using`, префиксы, токенизацию и совместимость эмбеддингов запроса и документа |
| С узким фильтром возвращается мало результатов | Выполни точный поиск с тем же фильтром. Проверь тип поля, число доступных точек, индекс payload и полноту ANN |
| После роста данных скачет p99 | Сопоставь с индексацией, размером неиндексированных сегментов, дисковым I/O и параллелизмом |
| Результат свежей записи иногда отсутствует | Проверь `wait`, режимы видимости, реплики, фильтр и выбранное поле вектора |
| Удалённый фрагмент снова появляется | Проверь запоздалые события, повторы, backfill и порядок записи версий |
| После обновления документ показан дважды | Проверь стабильность ID и удаление старых фрагментов |
| Гибрид даёт неожиданно слабый результат | Посмотри обе выдачи отдельно, проверь токенизацию, глубину кандидатов и обработку фильтра в каждой ветке |
| Векторное сходство высокое, а ответ бесполезен | Проверь разметочную релевантность, заголовки и границы фрагментов, разнообразие результатов и качество переранжирования |

Порядок настройки удобно привязать к узкому месту. Сначала зафиксируй ожидаемое качество и права доступа, затем проверь точный поиск. Если точный поиск даёт нужное качество, настраивай ANN и квантование под задержку. Если ошибки видны уже в точной выдаче, начни с модели, данных и способа формирования кандидатов.

## 12. Что могут спросить на техническом собеседовании

1. **Чем векторная БД отличается от библиотеки ANN?** В БД вокруг алгоритма есть хранение, обновления, метаданные, фильтры, сетевой доступ и восстановление. Библиотека предоставляет алгоритмы и структуры поиска для встраивания.
2. **Когда cosine и dot дают один порядок?** При единичной норме всех сравниваемых векторов. Объясни на формуле, как длина вектора влияет на скалярное произведение.
3. **Как работает HNSW и что меняет `hnsw_ef`?** Верхние уровни приводят поиск в нужную область, нижний расширяет набор кандидатов. Больший `hnsw_ef` даёт графу больше возможностей найти соседей ценой дополнительной работы.
4. **Почему top-10 с постфильтрацией бывает пустым?** Глобальные соседи могут принадлежать другим клиентам. Корректный top-10 строится внутри допустимого множества, а узкий фильтр может потребовать другого плана.
5. **Как Qdrant ищет по разреженным векторам?** Инвертированный индекс связывает ненулевые координаты со списками точек. В скалярное произведение входят только общие ненулевые координаты.
6. **Зачем RRF, если две ветки возвращают численные оценки?** Косинус и BM25 имеют разные шкалы. RRF объединяет места, поэтому не требует напрямую складывать эти оценки.
7. **Чем полнота ANN отличается от Recall@k по разметке?** У первой эталон — точные соседи в данном пространстве. У второго эталон — релевантные результаты, которые определила разметка.
8. **Чем шард отличается от реплики?** Шард содержит часть набора данных, реплика хранит ещё одну копию этой части. Первый помогает распределять объём, вторая — сохранять доступность.
9. **Что произойдёт после тайм-аута upsert?** Статус может быть неизвестен клиенту. Повтор с тем же ID и содержимым безопаснее, но при нескольких версиях требуется защита от запоздалых событий.
10. **Как сменить модель эмбеддингов без остановки поиска?** Построить новое пространство отдельно, догнать поток изменений, сравнить выдачу и переключить модель запросов вместе с коллекцией или именованным полем.
11. **Когда квантование ухудшит p99?** Например, если поиск берёт больше кандидатов для пересчёта и затем читает полноточные векторы с диска при холодном кэше.
12. **Почему поиск хорошего фрагмента ещё не гарантирует хороший RAG-ответ?** Контекст может содержать несколько противоречащих версий, а модель может выбрать устаревший фрагмент или сделать неподтверждённый вывод. Проверку retrieval и проверку генерации измеряют отдельно.
